# แผน BOQ ฉบับใช้งาน

**วันที่ 2026-11-15 (Asia/Bangkok) · Owner เลือกแบบ 2 · รอตรวจรายละเอียดก่อนลงมือ**

เอกสารนี้ขยาย [Roadmap #09 และตารางสิทธิ์ที่ตกลงกัน](./09-integrated-roadmap-and-it-decision-handoff.md#boq-operational-workflow)
เป็นแผนออกแบบและตรวจรับ ขอบเขตรอบนี้คือเอกสารในเครื่อง การแก้แอป,
migration, การรัน Docker และการปล่อยระบบรออนุมัติแยกกัน

ใช้ [เรื่องที่ Owner ตัดสินใจ](#wh-owner-decisions) และ

## 1. ขั้นตอนธุรกิจ

**แบบ 2 ที่ Owner เลือก** ใช้ BOQ ใบเดิมตลอดสามสถานะ
**ฉบับร่าง → เสนออนุมัติ → ฉบับใช้งาน**

1. **เสนออนุมัติ** จากหน้ารายละเอียด BOQ เดิม ใช้ข้อมูลฉบับร่างที่บันทึก
   ล่าสุด เมื่อผ่านการตรวจ ระบบล็อกเนื้อหาและออกรหัสชุดให้อัตโนมัติ
2. **พิมพ์ชุดเสนอ** จาก BOQ ใบนั้น แล้วนำเอกสารไปขอลงนามตามขั้นตอนจริง
   ของส่วนงาน ใช้วิธีอ้างอิงชุดที่ Owner จะยืนยันตาม §8
3. **บันทึกผลลงนาม** เมื่อหนังสือกลับมาแล้ว เปิด BOQ ใบเดิม ระบบแสดง
   รหัสชุดให้ผู้มีสิทธิ์ตรวจหลักฐานว่าหนังสือตรงกับชุดที่เปิดอยู่ แล้วกรอก
   **เลขที่หนังสือเต็ม** และ **วันที่หนังสือ** เมื่อบันทึกสำเร็จ ระบบเปลี่ยนเป็น
   **ฉบับใช้งาน** โดยใช้เนื้อหาชุดที่ล็อกไว้

คนเสนอ คนพิมพ์ และคนบันทึกผลอาจเป็นคนละคนตามสิทธิ์ใน §3
ระบบจดผู้ทำรายการและเวลา และจัดการการกดซ้ำอยู่เบื้องหลัง ผู้ใช้ดำเนินการ
เพิ่มเมื่อข้อมูลยังไม่ได้บันทึก ชุดไม่ตรงกัน หรือมีเหตุให้ถอนหรือแก้ไข

เมื่อต้องแก้ก่อนลงนาม ให้ผู้มีสิทธิ์ **ถอนกลับเป็นร่าง** ใบเดิมตามเงื่อนไข
ด้านล่าง หากลงนามแล้วและต้องแก้เนื้อหา ให้ **Copy** เป็นฉบับร่างใหม่
เพื่อเสนอและขอลงนามใหม่

Copy จากทั้งสามสถานะใช้สิทธิ์และเงื่อนไขเดิม ผลลัพธ์เป็นฉบับร่างใบใหม่เสมอ
รหัสชุดเสนอ หนังสือ และประวัติอนุมัติผูกกับต้นฉบับ เมื่อถอนชุดเสนอแล้ว
การเสนอครั้งถัดไปได้รหัสใหม่แม้เนื้อหาเหมือนเดิม

สถานะ **เสนออนุมัติ** ครอบคลุมทั้งช่วงก่อนลงนามและช่วงลงนามแล้วแต่ยังรอบันทึก
ผู้ถอนจึงต้องตรวจข้อเท็จจริงกับส่วนงานหรือผู้รับเอกสาร ข้อเสนอคือให้เก็บ
เหตุผล ผู้ยืนยัน และเวลาที่ตรวจสอบ หากยืนยันไม่ได้ ให้คงชุดไว้และประสาน Admin

## 2. การจับคู่หนังสือลงนามกับชุดเสนอ

1. **ตอนเสนอ** ออกรหัสชุดที่ไม่ซ้ำจากระบบในธุรกรรมเดียวกับการล็อก BOQ
   และบันทึกผู้เสนอ เวลา และลายนิ้วมือของข้อมูลที่จะพิมพ์ ใช้ลายนิ้วมือที่มี
   รุ่นของกติกาและเรียงข้อมูลอย่างคงที่ ครอบคลุมชื่อโครงการ ผู้จัดทำ วันที่ใน BOQ
   เส้นทาง ลำดับรายการ หมายเหตุ หน่วย ปริมาณ ราคาต่อหน่วย ยอดแต่ละระดับ
   รุ่น Catalog, ข้อมูล Factor F/VAT ที่ใช้ และรุ่นของแบบพิมพ์ที่จำเป็น
   ต่อการอ่านเอกสารย้อนหลัง หากข้อมูลส่วนใดมาจากทะเบียนที่แก้ได้ ให้ตรึง
   ค่าที่ใช้ในเอกสารขณะออกชุด
2. **ตอนพิมพ์** แสดงว่าเอกสารเป็น **ชุดเสนออนุมัติ** ส่วนตำแหน่งรหัสชุด
   และหลักฐานที่เชื่อมหนังสือกับชุดใช้ผลตัดสินใจตาม §8 การพิมพ์ซ้ำยังอ้างชุด
   เดิมในระบบ เมื่อจำเป็นต้องได้ไฟล์เดียวกับที่ส่งลงนาม ให้เรียกไฟล์ต้นฉบับ
   ที่เก็บไว้
3. **ตอนบันทึก** ผู้บันทึกตรวจอำนาจผู้ลงนาม หนังสือ และหน้าที่เกี่ยวข้อง
   โดยใช้หลักฐานตามวิธีที่จะรับรองเพื่อจับคู่กับชุดที่เปิดอยู่ในระบบ
   ถ้ามีการแก้ตัวเลขหรือรายการบนกระดาษ ให้ตรวจกรณีเอกสารไม่ตรงชุดก่อน
   บันทึกเลขที่เต็มและวันที่หนังสือตามเอกสาร
   เช่น `เอ็นที วทฐฐ./xxx` สำหรับส่วนวิศวกรรมท่อร้อยสาย ตัวอย่างของส่วน
   ปฏิบัติการคือ `เอ็นที ปทฐฐ./xxx` โดยต้องยืนยันผู้ลงนามก่อนเปิดใช้ในส่วนนั้น
   วันที่หนังสือเก็บแยกจากเวลาที่ระบบบันทึก แสดงปีไทยหรือสากลให้ชัดและตรวจวันจริงก่อนบันทึก
   หากต้องบันทึกวันลงนามเพิ่มให้ยืนยันจากแบบหนังสือจริง
4. **ตอนเปลี่ยนสถานะ** ฐานข้อมูลตรวจสิทธิ์ปัจจุบัน รหัสชุดที่เปิดอยู่
   สถานะ และลายนิ้วมือของเนื้อหาที่ล็อก แล้วบันทึกข้อมูลหนังสือ ประวัติ
   และสถานะฉบับใช้งานพร้อมกัน รหัสที่ถอนแล้วใช้บันทึกผลไม่ได้ การตรวจ
   ลายนิ้วมือยืนยันเนื้อหาที่ระบบเก็บ ผู้บันทึกยังเป็นผู้ตรวจลายเซ็นและ
   เอกสารจริง

ให้ใช้รหัสชุดระบุชุดเสนอในระบบ และเก็บเลขที่หนังสือเป็นข้อมูลอ้างอิงเอกสาร
หาก Owner ยืนยันว่าหนังสือหนึ่งฉบับครอบคลุมได้หลาย BOQ ให้ตรวจว่าหลักฐาน
เชื่อมหนังสือกับ BOQ และชุดเสนอของแต่ละใบตามวิธีใน §8 แล้วบันทึกทีละใบในรอบแรก

**เอกสารที่เก็บย้อนหลัง** ข้อเสนอเริ่มต้นคือให้ส่วนงานเก็บ PDF ชุดที่ออกเสนอ
และเอกสารลงนามในที่จัดเก็บเอกสารเดิม ระบบเก็บรหัส ลายนิ้วมือ รุ่นข้อมูลพิมพ์
ประวัติ และข้อมูลอ้างอิงที่ส่วนงานใช้จับคู่และค้นคืนเอกสารตามวิธีที่จะตกลง
หลังถอนแล้ว BOQ ใบเดิมกลับมาแก้ได้ จึงต้องอาศัยไฟล์ที่เก็บไว้หากต้องการ
เนื้อหาของชุดเดิม แบบพิมพ์อาจเปลี่ยนตามรุ่นแอป ให้ทดลองค้นคืนหนึ่งชุด
จากที่เก็บเอกสารจริงก่อนเลือกวิธีเก็บ ถ้าค้นคืนตามวิธีที่พิจารณาไม่ได้
ให้เสนอการเก็บ PDF ชุดเสนอในพื้นที่ควบคุมสิทธิ์เป็นทางเลือกพร้อมขอบเขต

### เอกสารผิดชุดและการแก้หลังบันทึก

- **เลือกผิดใบหรือกรอกผิดก่อนบันทึก** กลับไปเลือกชุดที่ตรงและยังเปิดอยู่
  หรือกรอกใหม่ตามเอกสารจริง
- **อ้างชุดที่ถอนแล้ว หาชุดไม่พบ หรือเนื้อหาต่างกัน** ส่งให้ Admin ตรวจและ
  ประสานส่วนงาน ชุดที่ยังเปิดอยู่คงสถานะเสนออนุมัติ ส่วนชุดที่ถอนแล้วคงผลถอน
  ให้บันทึกผลได้เฉพาะกับชุดที่เปิดอยู่และมีเอกสารลงนามตรงกัน หากใช้เนื้อหา
  อีกชุด ให้จัดทำเอกสารแก้ไขหรือขอลงนามชุดนั้นตามขั้นตอนของหน่วยงาน
- **กรอกเลขหรือวันที่ผิดหลังบันทึก แต่เอกสารและเนื้อหาตรงชุด** Admin แก้
  เฉพาะข้อมูลอ้างอิงและบันทึกค่าเดิม ค่าใหม่ เหตุผล ผู้แก้ และเวลา
- **บันทึกอนุมัติผิดชุด** Admin ระงับการใช้ฉบับนั้นสำหรับ TOR พร้อมเหตุผล
  และประวัติ เพื่อหยุดการใช้ระหว่างตรวจข้อผิดพลาด
- **มีฉบับใหม่มาแทนตามปกติ** ฉบับเดิมที่ยังถูกต้องใช้ต่อได้ระหว่างที่ใบใหม่
  เป็นร่างหรือเสนออนุมัติ เมื่อใบใหม่มีผลลงนามของตัวเอง ให้ Admin ระบุชุดที่
  ใช้ต่อและบันทึกวันที่/เหตุผล ช่องทางดูหรือพิมพ์สำหรับ TOR ต้องตรวจฉบับ
  ที่ยังใช้ได้เมื่อเปิด

## 3. สิทธิ์และการมอบหมาย

| คำสั่ง | ผู้มีสิทธิ์ |
|---|---|
| **เสนออนุมัติ** | ผู้จัดทำหรือผู้รับผิดชอบที่ได้รับมอบหมาย BOQ รายใบและยังมีสิทธิ์แก้ไข ผู้จัดการส่วนในส่วนที่รับผิดชอบ และ Admin ทุกส่วนงาน |
| **ถอนกลับเป็นร่าง** | ผู้จัดทำสำหรับใบของตนที่ยังอยู่ในขอบเขตสิทธิ์แก้ไข ผู้รับมอบหมายที่มีสิทธิ์ถอนในส่วนงาน ผู้จัดการส่วนในส่วนที่รับผิดชอบ และ Admin ทุกส่วนงาน |
| **บันทึกผลลงนาม** | Admin ผู้จัดการส่วนในส่วนที่รับผิดชอบ และผู้รับมอบหมายที่มีสิทธิ์บันทึกผลในส่วนงาน |
| **แก้ข้อมูลอ้างอิงที่บันทึกผิด ระงับฉบับ หรือกำหนดฉบับที่ใช้ต่อสำหรับ TOR** | Admin |

หน้า Admin ให้เลือกบัญชีและส่วนงานแล้วติ๊ก **ถอนชุดเสนออนุมัติ** และ
**บันทึกผลลงนาม** แยกกัน แสดงว่าสิทธิ์ใดมาจากบทบาทหรือผู้จัดทำ และสิทธิ์
ใดมาจากการติ๊ก ผู้รับมอบหมาย BOQ รายใบใช้สิทธิ์แก้ร่างเพื่อเสนอ ส่วนการถอน
ใช้สิทธิ์ตามบทบาทหรือสิทธิ์ถอนที่มอบแยก

ตรวจบัญชีที่ยังใช้งาน สิทธิ์เข้าถึง BOQ ส่วนงานของ BOQ ที่ตรวจสอบแล้ว และ
สิทธิ์ล่าสุดเมื่อฐานข้อมูลรับคำสั่ง สำหรับผู้รับมอบหมาย ให้ส่วนงานจริงของ
ผู้ใช้ตรงกับส่วนงานที่ได้รับสิทธิ์และส่วนงานของ BOQ ผู้จัดการฝ่ายใช้สิทธิ์เดิม
ในงานทั่วไป ส่วนสิทธิ์เฉพาะ workflow ใช้ตารางข้างต้น ข้อเสนอคือให้การมอบหมาย
เดิมสิ้นผลเมื่อย้ายส่วนงาน และให้ Admin มอบใหม่หากย้ายกลับ เก็บประวัติผู้มอบ
หรือถอนสิทธิ์ เวลา คนรับ ส่วนงาน และคำสั่ง

ให้ Admin ตรวจกรณี BOQ เก่าที่ต้นทางส่วนงานว่างหรือขัดกันจากหลักฐาน
การพิมพ์ชุดเสนอใช้สิทธิ์ดู BOQ ร่วมกับสิทธิ์งานที่เกี่ยวข้อง เสนอให้ผู้มีสิทธิ์
เสนอหรือบันทึกผลพิมพ์ได้ตามขอบเขตเดิม กรรมการ TOR ใช้แผน Viewer แยก

ผู้จัดการส่วนวิศวกรรมท่อร้อยสายเป็นผู้ลงนามตามที่ Owner ยืนยัน ส่วนคำนำหน้า
หนังสือระบุส่วนงานของเอกสาร ผู้ลงนามของส่วนปฏิบัติการต้องยืนยันก่อนเปิดใช้
กับหนังสือของส่วนนั้น

ตรวจ grants, RLS และ trigger ของ Create/Update ก่อนใช้ `org_id`,
`department_id` และ `sector_id` ตัดสินสิทธิ์ ตรวจทั้งลำดับชั้นและที่มาของ
สังกัด เช่น เจ้าของร่างอ้างส่วนงานอื่นที่มีอยู่จริงผ่าน API โดยตรง ให้ส่วนงาน
ที่ผ่านการตรวจถูกตรึงพร้อมชุดเสนอและใช้กับคำสั่งของชุดนั้นตลอดอายุชุด

## 4. ฐานข้อมูลและการเขียนโปรแกรม

**ใช้ BOQ ใบเดิมเป็นหลัก** คงกราฟ `boq` / `boq_routes` / `boq_items`
ไว้ เพิ่มข้อมูลสถานะ workflow ที่ยืนยันได้จากชุดเสนอและผลลงนาม มีแหล่ง
อ้างอิงสถานะเดียวสำหรับหน้า List, Edit และ Print และเก็บประวัติเหตุการณ์แบบ
เพิ่มรายการใหม่อย่างเดียว ค่ารุ่นเก่า เช่น `approved`, `pending_review`
และ `pending_approval` ต้องผ่านการแยกความหมายก่อนเลือกโครงสร้างคอลัมน์
แนะนำให้เก็บเลขที่และวันที่หนังสือเป็นคนละช่อง และเก็บเหตุผลระงับการใช้

ก่อนส่งตรวจ implementation ให้ระบุว่าแต่ละกติกาบังคับอยู่ที่ใดและมีเคส
ทดสอบใดพิสูจน์ ถ้ากติกาเรื่องสิทธิ์ การล็อก หรือการจับคู่เอกสารยังทำงาน
ไม่ครบ ให้แก้ในชุดนั้นก่อนเปิดใช้ ส่วนงานต่อยอด เช่น Viewer/TOR,
แม่แบบชื่อ และการรับรอง BOQ เก่า ให้ระบุขอบเขตและลำดับตาม §8–9

- **บังคับที่ฐานข้อมูล** ให้มีคำสั่งฐานข้อมูลเฉพาะเสนอ ถอน บันทึกผล
  และจัดการแบบ Admin คำสั่งตรวจผู้ใช้และ BOQ เป้าหมายในธุรกรรมเดียวกับ
  การเปลี่ยนสถานะและลงประวัติ จำกัดสิทธิ์เรียกคำสั่งและเก็บตารางประวัติ/
  การมอบหมายไว้ภายใน ใช้รหัสคำขอสำหรับตรวจผลหากตอบกลับขาดหายและกันประวัติ
  ซ้ำ ผูกรหัสคำขอกับผู้ใช้ คำสั่ง ชุดเป้าหมายและข้อมูลที่ส่ง คำขอเดิมที่
  มีข้อมูลเดิมได้ผลเดิม ส่วนรหัสเดิมกับข้อมูลคนละชุดให้ปฏิเสธ การถอนกับ
  บันทึกผลที่ชนกันบนชุดเดียวต้องสำเร็จเพียงหนึ่งทาง
- **ล็อกทุกทางเขียน** ครอบคลุมหัว BOQ, เส้นทาง, รายการ, Save RPC,
  การเขียนตรงผ่าน Data API, การย้ายลูกข้าม BOQ ทั้งต้นทางและปลายทาง และ
  การลบที่กระทบลูก รวมถึงคำสั่ง Admin กฎ S0 เดิมใช้คุมบทบาทผู้เขียน ส่วน
  ชุดนี้เพิ่มการป้องกันตามสถานะและคงสิทธิ์เดิมของร่างทั่วไป สำหรับร่างที่เคย
  ถอนชุดเสนอ เสนอให้คงประวัติ และใช้การเก็บเข้าประวัติแทนการลบที่ทำให้
  ตามรหัสชุดเดิมไม่ได้
- **จัดการการแข่งกันของคำสั่ง** ใช้ธุรกรรมสั้น ลำดับล็อกต้องเข้ากันกับ
  Save/Copy ที่ล็อกข้อมูลผู้ใช้ก่อน BOQ และ Copy ล็อกเส้นทางกับรายการต่อ
  ตรวจช่องทางที่จะยังเขียนลูกโดยตรงก่อนเลือกกลไกสุดท้าย เพราะ trigger
  ที่ไปล็อก BOQ หลังแถวลูกอาจสลับลำดับกับ Save ต้องทดสอบกับ PostgREST
  จริง ทางที่แนะนำให้ประเมินก่อนคือให้ช่องทางเขียนที่รองรับล็อก BOQ ก่อน
  เขียนลูกและใช้การอนุญาตเฉพาะช่องทางที่จำเป็น ตรวจผู้เรียกจริงก่อนจำกัด
  สิทธิ์เขียนตรง การเสนอให้เปรียบเทียบกับข้อมูลที่ผู้ใช้เพิ่งตรวจ แม้คำสั่ง
  Save อื่นสำเร็จก่อนกดเสนอ หากข้อมูลเปลี่ยนต้องให้เปิดตรวจใหม่
- **คุมข้อมูลที่ออกเอกสาร** ให้หน้าพิมพ์ชุดเสนอและฉบับใช้งานอ่านข้อมูล
  ที่ครบและสอดคล้องกันสำหรับรหัสชุดเดียวจากฝั่งเซิร์ฟเวอร์ ใช้ค่าอ้างอิง
  และตัวเลขที่บันทึกไว้ รวมถึงกติกาการปัดเศษ/จัดสรรต่อเส้นทางที่ Owner
  รับรองใน D0 เมื่อราคา Factor F หรือยอดที่จำเป็นยังไม่ครบ ให้แจ้งแก้ที่
  ฉบับร่างก่อนออกชุด รายการศูนย์และกรณีพิเศษใช้เกณฑ์ D0 ที่อนุมัติ

## 5. หน้าจอที่เสนอ

ให้เริ่มคำสั่งเกี่ยวกับสถานะจากหน้ารายละเอียด BOQ เดิม แสดงปุ่มหลักตามสถานะ
และสิทธิ์ ฟอร์มบันทึกผลมีสองช่อง ระบบแสดงรหัสชุดของ BOQ ที่เปิดอยู่
อัตโนมัติ รูปแบบแสดงข้อผิดพลาดและการตรวจรับให้ยึดขั้นตอนใน §1

| หน้า | สิ่งที่ผู้ใช้เห็นหรือทำ |
|---|---|
| **รายการ BOQ** | ป้ายฉบับร่าง / เสนออนุมัติ / ฉบับใช้งาน แสดงคำสั่งตามสิทธิ์ของแต่ละใบ และเข้าถึง Copy ตามกฎเดิม |
| **รายละเอียดฉบับร่าง** | แก้ตัวเลขและบันทึกตามเดิม ก่อนเสนอให้ตรวจชื่อโครงการ ยอด และรุ่นข้อมูล หากมีการแก้ค้างหรือตัวเลขยังไม่ครบให้กลับไปบันทึกหรือตรวจรายการ |
| **รายละเอียดเสนออนุมัติ** | เนื้อหาอ่านอย่างเดียว แสดงรหัสชุด ใครเสนอเมื่อไร และมีปุ่ม **พิมพ์ชุดเสนอ** กับ **บันทึกผลลงนาม** หรือ **ถอนกลับเป็นร่าง** ตามสิทธิ์ เปิดฟอร์มบันทึกพร้อมรหัสชุดและช่องเลขที่/วันที่หนังสือ ฟอร์มถอนมีเหตุผลและการยืนยันว่ายังไม่ลงนามและหยุดใช้ชุดที่ส่งออกไปแล้ว |
| **หน้าพิมพ์** | แยกฉบับร่างจากแบบเสนออนุมัติให้เห็นบนกระดาษ การแสดงรหัสบนเอกสารขึ้นกับผลตัดสินใจใน §8 ตรวจชุดในระบบ สถานะ และสิทธิ์เมื่อเปิดชุดและก่อนเริ่มคำสั่งพิมพ์ หากชุดหมดอายุจากการถอนให้กลับไปหน้ารายละเอียด เอกสารที่พิมพ์หรือดาวน์โหลดไปแล้วต้องเรียกคืนทางส่วนงาน |
| **รายละเอียดฉบับใช้งาน** | แสดงเลขที่/วันที่หนังสือ รหัสชุดและประวัติ มีหน้าอ่านและพิมพ์ตามสิทธิ์ กับปุ่ม Copy ส่วน Admin เห็นคำสั่งแก้ข้อมูลอ้างอิง ระงับ และเลือกฉบับใช้ต่อพร้อมเหตุผล |
| **Admin → ผู้ใช้** | ส่วนมอบหมายรายส่วนงานในหน้ารายละเอียดผู้ใช้เดิม สองช่องติ๊กพร้อมขอบเขตและผลเมื่อเอาติ๊กออก |

ใช้ theme NT และองค์ประกอบหน้าจอเดิม ทดสอบไทยยาว มือถือ และคีย์บอร์ด
เมื่อมีคนเปลี่ยนสถานะระหว่างเปิดหน้า ให้รีเฟรชก่อนทำรายการ เมื่อผลคำสั่ง
ไม่แน่ชัด ให้แสดงว่ากำลังตรวจผลรายการเดิมด้วยรหัสคำขอ

## 6. BOQ เก่า

| กรณี | แนวทางที่เสนอ |
|---|---|
| ฉบับร่างเก่าที่ข้อมูลและสังกัดครบ | ใช้งานร่างตามสิทธิ์เดิม แล้วเข้าสู่สามสถานะเมื่อกดเสนอครั้งแรก |
| มีสถานะเก่าคล้ายอนุมัติหรือมีหนังสือจริงแต่ยังไม่มีรหัสชุด | ให้ Admin ตรวจเป็นรายใบตามเกณฑ์ที่ Owner รับรอง ตรวจเอกสาร ยอด เนื้อหา และส่วนงานก่อนกำหนดขั้นตอนรับรองย้อนหลัง เก็บสถานะเดิมและหลักฐานไว้ระหว่างรอ |
| ข้อมูลส่วนงาน ราคา Factor F หรือยอดที่จำเป็นขาด หรือเทียบกับเอกสารเดิมไม่ได้ | ให้เก็บและเปิดดูตามสิทธิ์เดิม ระงับการออกชุดเสนอและการส่งต่อเป็นฉบับใช้งาน หากต้องการใช้งานชุดใหม่ ให้ทำร่างให้ครบและส่งลงนามตามปกติ |

เสนอให้รุ่นแรกเริ่มจากร่างที่ตรวจได้ครบและเลื่อนการรับรองย้อนหลังเป็นงาน
รายกรณี หากมี BOQ เก่าจำเป็นสำหรับ TOR ให้ Owner เลือกหลักฐานที่จะยอมรับ
และทำแผนทดสอบเฉพาะก่อนเปิดเส้นทางรับรองย้อนหลัง

## 7. แผนทดสอบบน Docker แยก

**สถานะการทดสอบทั้งหมด: NOT RUN** แผนเสนอใช้ Docker แยกพร้อม baseline
โครงสร้างและสิทธิ์หลัง 033 ที่ตรวจสอบที่มาได้ ใช้ฐานและบัญชีจำลองของชุด
ทดสอบเท่านั้น ก่อนรันให้ยืนยัน Docker context, container/volume, image digest,
API และฐานเป้าหมาย, PostgREST, grants/RLS/functions ที่เกี่ยวข้อง, loopback
และการกัน egress ไปบริการจริง ใช้ baseline โครงสร้างหลัง 033 แบบข้อมูล
จำลองโดยรักษา 027–033 และฐาน Docker เดิม หากหลักฐาน baseline ไม่ครบให้พัก
การทดสอบ ขออนุมัติ exact fixture, target, cleanup และ migration ใหม่ก่อนรัน
[แนวทางฐานทดสอบของ repo](../../06_engineering/LOCAL_DATABASE_PARITY_PLAN.md)
· [Docker port publishing](https://docs.docker.com/engine/network/port-publishing/)

ใช้บัญชีและ BOQ จำลองของส่วนงานที่ Owner อนุมัติให้เข้าทดลองสำหรับขั้นตอนครบ
รวม Admin ผู้จัดการส่วน ผู้จัดทำ ผู้รับมอบหมายรายใบ ผู้รับมอบหมายถอนอย่างเดียว/
บันทึกผลอย่างเดียว และผู้ไม่มีสิทธิ์หรือถูกถอนสิทธิ์ เพิ่มส่วนงานอื่นเพื่อทดสอบ
การปฏิเสธสิทธิ์ข้ามส่วน และครอบคลุมกรณีส่วนงานว่าง ผู้จัดทำไม่ปรากฏ และสถานะเก่า
ให้รายงานขั้นตอนครบของส่วนงานนอกขอบเขตเป็น **NOT RUN** รวมถึงส่วนปฏิบัติการ
หากยังรอยืนยันผู้ลงนามหรือยังไม่รวมในขอบเขตทดลอง

| กลุ่ม | เกณฑ์ผ่าน |
|---|---|
| **ขั้นตอนครบ** | ร่าง → เสนอ → พิมพ์ชุดเสนอ → จับคู่หนังสือจำลองกับชุดที่ล็อกและบันทึก → ใช้งาน หัว BOQ เส้นทาง รายการ และยอดตรงตลอดขั้นตอน ใช้รูปแบบหนังสือและอำนาจลงนามที่ยืนยันสำหรับแต่ละส่วนงานที่เข้าทดลอง |
| **ถอน/เสนอซ้ำ/หนังสือผิดชุด** | ถอนกลับใบเดิม รหัสชุดใหม่ต่างจากเดิมแม้เนื้อหาเดิม หลักฐานที่อ้างถึงชุดที่ถอนหรือคนละชุดถูกปฏิเสธ ชุดที่ลงนามแล้วเข้าทาง Copy หรือให้ Admin ตรวจข้อยกเว้น |
| **ขอบเขตสิทธิ์** | ทดสอบครบตามตาราง รวมสองส่วนในฝ่ายเดียวกันและส่วนควบคุมต่างฝ่าย ผู้รับมอบหมายรายใบ สิทธิ์ติ๊กแต่ละช่อง ถอดสิทธิ์หรือย้ายออก/กลับขณะใช้ session เดิม ผู้ใช้ถูกระงับหรือไม่มีสิทธิ์ ปลอมสังกัดผ่าน API ตอนสร้างและแก้ และเปิด URL ชุดพิมพ์ตรง |
| **ฐานข้อมูลล็อกและกดพร้อมกัน** | ทดสอบ Save ชนเสนอทั้งสองลำดับ ถ้าข้อมูลหลัง Save ต่างให้ตรวจใหม่ ทดสอบเพิ่มหรือย้ายลูกชนการล็อก ถอนชนบันทึกผล และเพิกถอนสิทธิ์ชนบันทึกผล ทดสอบ I/U/D โดยตรงทั้งสามตารางรวม Admin, cascade และผลตอบกลับไม่ถึง กรณีถูกปฏิเสธให้ตรวจจำนวนแถวและข้อมูลจริงพร้อมประวัติ |
| **ตัวเลขและหน้าพิมพ์** | Print/PDF/Excel ใช้ชื่อ รายการ ปริมาณ ราคา Factor F และยอดชุดเดียวกันตาม D0 ตรวจ PDF จริงหลายหน้าและการแสดงรหัสตามวิธีที่รับรอง รวมกรณีหลายเส้นทาง การปัดเศษ ค่าอ้างอิงเริ่มต้นเปลี่ยน และข้อมูลไม่ครบ หน้าเก่าหลังถอนเริ่มพิมพ์ชุดเดิมไม่ได้ |
| **หลักฐานและการค้นคืน** | ใช้หลักฐานตามวิธีที่รับรองเพื่อจับคู่เอกสารลงนามกับชุดที่ล็อกและค้นคืนเอกสารต้นฉบับ หากรองรับหนังสือหนึ่งฉบับต่อหลาย BOQ ให้แยกจับคู่และบันทึกผลของแต่ละใบ หากไม่รองรับ ให้ทดสอบเงื่อนไขการใช้เลขซ้ำที่ตกลง |
| **Copy และ BOQ เก่า** | Copy จากทั้งสามสถานะได้ร่างใหม่พร้อมผล 031 เดิม ไม่มีหนังสือหรือประวัติอนุมัติติดมา รวมทั้งโหมด Factor F เดิม สถานะเก่าไม่ถูกยกระดับเอง ตรวจ Draft Create/Save/Print และแยกการลบร่างที่ไม่เคยเสนอจากร่างที่ถอนชุดแล้ว |
| **จัดการฉบับใช้งานและ UI** | Admin แก้เลข/วันที่ได้พร้อม audit ระงับฉบับผิดพร้อมประวัติ ฉบับระงับไม่ผ่านเงื่อนไขคัดไปใช้สำหรับ TOR ทดสอบหน้าจอคอม/มือถือ คีย์บอร์ด และข้อผิดพลาดที่ผู้ใช้ทำต่อได้ |
| **ความเข้ากันได้และ rollback** | ทดสอบฐานใหม่กับแอปเดิมก่อนเปิด workflow และจุด rollback หลังมีชุดเสนอจริง ร่างปกติยังทำงานได้ ส่วนหน้าแก้ ลบ และ Print เดิมจัดการชุดที่ล็อกตาม §9 |

รัน focused tests, lint, TypeScript และ Turbopack build บน Node 24 ตาม baseline
แอป บันทึกผลรายกรณี PASS/FAIL/NOT RUN พร้อม source/target และข้อจำกัด
ตรวจว่าข้อมูลเดิมไม่ได้เปลี่ยน ปิด session/บริการของชุดทดสอบและเก็บหลักฐาน
ที่ไม่มีข้อมูลลับ หากผลเขียนไม่ชัดให้หยุดตรวจสถานะก่อนส่งคำสั่งซ้ำ

## 8. เรื่องที่ Owner ตัดสินใจ

ใช้ตัวอย่างหนังสือและหน้าที่แนบหนึ่งชุดต่อส่วนงานที่จะเปิดใช้ ระบุให้เห็น
ตำแหน่งอ้าง BOQ ผู้ลงนาม และวิธีค้นเอกสารเดิม ตัวอย่างที่ใช้ทบทวนแผน
สามารถปิดข้อมูลส่วนบุคคลและข้อมูลที่ไม่จำเป็นได้

| เรื่อง | ข้อเสนอให้ตรวจ | ผลต่อลำดับงาน |
|---|---|---|
| ผู้ลงนาม | วิศวกรรมยืนยันแล้ว ให้ระบุผู้มีอำนาจสำหรับส่วนปฏิบัติการ เพิ่มส่วนปฏิบัติการเมื่อยืนยันได้ | ขอบเขตส่วนงานสำหรับเปิดใช้ |
| จับคู่และเก็บเอกสาร | รอเลือกตำแหน่งรหัสชุดระหว่างบน BOQ ที่พิมพ์ บนใบนำเสนอหรือทะเบียน และเฉพาะในระบบ ใช้ตัวอย่างจริงยืนยันว่าหลักฐานตามวิธีที่เลือกเชื่อมหนังสือลงนามกับ BOQ และชุดที่ล็อกได้ รวมถึงค้นคืน PDF ต้นฉบับพร้อมหนังสือได้ | กำหนดแบบพิมพ์และหลักฐาน |
| หนังสือหนึ่งฉบับกับหลาย BOQ | หากใช้ได้ ให้บันทึกทีละ BOQ และยืนยันหลักฐานที่ผูกหนังสือกับแต่ละใบและชุดของใบนั้นตามวิธีที่เลือก หากใช้ไม่ได้ ให้ตรวจการใช้ซ้ำตามเลขหนังสือเต็มและวันที่ในขอบเขตที่ตกลง | กำหนดเงื่อนไขตรวจเลขซ้ำ |
| ผู้พิมพ์ชุดเสนอ | ให้ผู้มีสิทธิ์เสนอหรือบันทึกผลและมีสิทธิ์ดู BOQ ใบนั้นพิมพ์ได้ หากเจ้าหน้าที่พิมพ์จริงเป็นอีกคน ให้ระบุบทบาทจากขั้นตอนงานจริง | ขอบเขตหน้าพิมพ์และสิทธิ์ |
| BOQ เก่า | เริ่มจากร่างที่พร้อม พิจารณาการรับรองย้อนหลังเป็นรายกรณีเมื่อมีงานต้องใช้ | กำหนดขอบเขตชุดแรก |

**ข้อเสนอเดิมวันที่ 2026-11-15:** ให้แสดงรหัสชุดบน BOQ และเอกสารแนบทุกหน้า
และให้หนังสืออ้างรหัสโดยตรงหรือผ่านเอกสารแนบ ข้อเสนอนี้ยังรอการตัดสินใจ

ใช้ตัวอย่างที่ตรวจรับแล้วระบุค่าที่ต้องตรงตั้งแต่รายการ/เส้นทางถึงยอด BOQ

## 9. ลำดับลงมือและวิธีย้อนแอปที่เสนอ

1. ทบทวนข้อ §8 และขอบเขตตัวเลข ยืนยันส่วนงานทดลอง และใช้ตัวอย่างกระดาษ
   ทำแบบร่างหน้าจอ แบบพิมพ์ และวิธีจับคู่หลักฐานให้ Owner ตรวจ
2. เสนอรายการไฟล์และ migration แบบเจาะจง พร้อมแผนข้อมูลจำลอง Docker แยก
   หลังอนุมัติจึงทำฐานข้อมูล แอป และชุดทดสอบ ตรวจ workflow จากร่างถึง
   ใช้งานครบทั้ง API และหน้าจอ รวมทดสอบแอปเดิมกับฐานใหม่
3. เมื่อมีผล Docker ครบ ให้เสนอแผนปล่อยแยก แนะนำให้เตรียมฐานข้อมูลที่
   รองรับแอปเดิมและเริ่มโดยปิดการออกชุดใหม่ เปิดเมื่อแอปและหน้าพิมพ์
   ที่รองรับพร้อมและได้รับอนุมัติ เกณฑ์ผ่านก่อนเปิดคือร่างเดิมยังใช้งานได้
   สิทธิ์และการล็อกผ่าน หลักฐานจับคู่และค้นคืนได้ และยอดออกเอกสารตรงตาม D0
4. หากมีปัญหาหลังเปิดใช้ ให้หยุดออกชุดใหม่ เก็บชุดที่มีอยู่และประวัติไว้
   แอปรุ่นก่อนอาจยังแสดงปุ่มแก้หรือลบ ฐานข้อมูลต้องปฏิเสธกับชุดที่ล็อก
   และต้องพิสูจน์ว่าหน้าพิมพ์รุ่นก่อนตรวจสิทธิ์ สถานะ และรองรับวิธีจับคู่
   หลักฐานที่รับรองแล้ว หากขาดข้อใด ให้ปิดเส้นทางนั้นสำหรับชุดที่เข้าสู่
   workflow หรือเลือกแอปจุด rollback ที่รองรับแล้ว
   ใช้สำเนาเอกสารควบคุมที่เก็บไว้สำหรับงานกระดาษระหว่างแก้ปัญหา

Viewer/TOR ทบทวนหลังมีฉบับใช้งานที่ตรวจรับแล้ว แม่แบบชื่อโครงการของ Admin
ทำเป็นงานแยกเมื่อรูปแบบชื่อของงานตามแผน งานจุด และงานปรับปรุงพร้อม
